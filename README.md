# focuspin AI — бекенд

[![CI](https://github.com/SARFEX/focuspin-backend/actions/workflows/ci.yml/badge.svg)](https://github.com/SARFEX/focuspin-backend/actions/workflows/ci.yml)

OpenAI-chat-completions-совместимый фасад над DeepSeek для мобильного
приложения focuspin. Приложение присылает свой «магический» запрос обычным
языком, бекенд возвращает **только** валидный канонический JSON команд
планировщика — сырой текст модели наружу не выходит никогда. Ноль runtime-
зависимостей, хранилище — `bun:sqlite`.

## Как это работает

```
приложение focuspin
   │  POST /v1/chat/completions
   │  Authorization: Bearer <deviceId>
   ▼
пин системного промпта → лимиты (HMAC-хеши device id/IP) → DeepSeek
   ▼
гард валидации команд → канонический JSON в choices[0].message.content
```

Единственный продуктовый путь — `POST /v1/chat/completions` (формат тела и
ошибок — [contract/api.md](contract/api.md)). Ответ 200 — форма OpenAI
`chat.completion`, содержательное поле одно: `choices[0].message.content` —
строка `{"commands":[...]}` после гарда. Заголовок `x-focuspin-contract:
commands-v4` — версия контракта.

## Механизмы защиты

- **Пин промпта.** Сервер не проксирует произвольные запросы: системное
  сообщение обязано побайтово совпасть с закреплённым промптом v4, иначе 400.
  Приложение не может попросить модель ни о чём другом.
- **Пин каркаса запроса.** `user`-сообщение тоже проверяется: приложение
  всегда пишет его по одному шаблону (дата → список задач → запрос в
  «ёлочках»). Произвольный «чат» через OpenAI-совместимый клиент — переводы,
  эссе за счёт ключа сервера — отбивается по форме ещё до вызова модели.
- **Гард валидации.** Ответ модели проходит строгую схему команд
  (`contract/schema-v4.md`) и каноническую пересборку; мусор, prose, markdown
  и посторонние поля до приложения не доходят (в худшем случае — 502
  `contract_violation`).
- **Потолок генерации.** Каждый вызов upstream уходит с `max_tokens`
  (`MAX_COMPLETION_TOKENS`, дефолт 8000 ≈ максимум схемы: 30 команд с
  описаниями): стоимость любого запроса детерминирована, «простыня» за счёт
  ключа сервера невозможна.
- **Никаких секретов у клиента.** Ключ DeepSeek живёт только на бекенде;
  device id — не секрет, а merely идентификатор.
- **Приватность.** В БД и логах нет сырых device id и IP — только
  HMAC-хеши; содержимое сообщений не логируется. Единственное осознанное
  исключение — реферальный контур (см. «Рефералы и статистика установок»):
  там для ручной проверки накрутки хранятся email, сырой IP (с ретеншном) и
  ссылки на посты; device id и там — HMAC-хеш.
- **Предохранители расходов.** Глобальные дневные потолки запросов и токенов
  не дают атаке сжечь ключ DeepSeek даже в худшем случае.

## Ярусы лимитов

Значения задаёт оператор: все `LIMIT_*`/`GLOBAL_*` **обязательны**, дефолтов
в коде нет — сервер не стартует без явных значений, фактические пороги
деплоя не являются публичной константой. Числа ниже — стартовый пример из
[.env.example](.env.example).

| Ярус | Лимит | Что отсекает |
|---|---|---|
| IP / минута | 15 | Лобовая атака с одного адреса |
| IP / час | 60 | Скриптовый перебор |
| IP / сутки | 300 | Фоновый абьюз |
| Подсеть /24 · /64 / сутки | 1200 | Ботнет из одной сети |
| Разные device id с одного IP / сутки | 6 | Ротация идентификаторов |
| Устройство / минута | 6 | Долбёжка кнопкой |
| Устройство / час | 15 | Активный абьюз |
| Устройство / сутки | 50 | Норма на устройство |
| Свежее устройство (< 24 ч) / сутки | 15 | Делает ротацию невыгодной |
| Contract fail / устройство / час | 10 | Систематическая порча контракта |
| Глобально: в полёте | 8 | Перегрузка upstream (429 `busy`) |
| Глобально: запросы / сутки | 20000 | Потолок расходов на ключ |
| Глобально: токены / сутки | 25 000 000 | Потолок расходов на ключ |

Окно «сутки» — UTC. Отказ — 429 `rate_limited` с `Retry-After`. Все пороги
задаются env-переменными (`LIMIT_*`, `GLOBAL_*` — см.
[.env.example](.env.example) и [ops/DEPLOY.md](ops/DEPLOY.md)).

## Идентификация без аккаунта

Устройство идентифицирует себя 32-hex `deviceId` (создаётся приложением локально,
опционально с суффиксом `_<счётчик>` ротации). Учёт ведётся по
HMAC-хешам device id и IP: сервер помнит «первое появление» устройства —
молодым устройствам суточная квота понижена (15 против 50), а с одного IP за
сутки учитывается не более 6 разных устройств. Итог: аккаунт не нужен,
анонимность сохранена, а ротация идентификаторов с одного IP становится
невыгодной.

## Рефералы и статистика установок

Дополнение к основному пути: сборка `play` приложения получает реферальную
ссылку, шлёт анонимное событие первой установки и заявки «Premium за пост».
Решение о выдаче Premium принимает владелец вручную по админ-таблицам.
Формат запросов и ответов — [contract/api.md](contract/api.md).

| Путь | Назначение |
|---|---|
| `POST /v1/referral/code` | email → код и ссылка `https://<домен>/i/<код>` (один email — один код, владение email не подтверждается) |
| `POST /v1/install` | событие первого запуска (`ref_code?`, `source`, `build`, версии, локаль) → 204, идемпотентно по deviceId |
| `POST /v1/post-claim` | заявка «Premium за пост»: email + https-ссылка → 202 |
| `GET /i/:code` | 302 на Google Play (`PLAY_PACKAGE_ID`) с `referrer=<код>` |
| `GET /admin/referrals`, `GET /admin/installs/stats`, `GET /admin/post-claims`, `POST /admin/post-claims/:id` | админка под `Authorization: Bearer <ADMIN_TOKEN>` |

- **Админка выключена по умолчанию:** без `ADMIN_TOKEN` все `/admin/*` отвечают
  404. Токен — только из окружения (≥ 32 символов, `openssl rand -hex 32`),
  сравнивается в постоянное время, в логи не попадает.
- **Лимиты** — те же дневные счётчики на устройство/IP/email, значения
  обязательны в env (`LIMIT_REFERRAL_DEVICE_DAY`, `LIMIT_REFERRAL_IP_DAY`,
  `LIMIT_INSTALL_IP_DAY`, `LIMIT_POST_CLAIM_EMAIL_DAY`).
- **Какие данные хранятся.** `referral_codes` — email и код; `install_events` —
  HMAC-хеш device id, ref-код, источник, сборка, версии приложения/ОС, локаль,
  время и **IP клиента**; `post_claims` — email, ссылка, статус решения.
  IP собирается для защиты от накрутки и проверки реферальных установок —
  **это нужно указать в политике конфиденциальности и в Play Data safety**
  (email, технические данные/IP, срок хранения). IP определяется той же
  логикой, что у лимитера (`TRUST_PROXY` → последний элемент `X-Forwarded-For`).
- **Ретеншн IP.** `IP_RETENTION_DAYS` (обязателен, пример — 90): запись об
  установке остаётся, но поле `ip` обнуляется по истечении срока; чистка идёт
  на старте и раз в час. Срок хранения email и заявок автоматикой не
  ограничен — удаление вручную по запросу пользователя.
- В админ-таблице `device_id` — HMAC-хеш: сырой id в БД не пишется (инвариант
  сохранён), сырыми хранятся лишь email и IP. Смена `HMAC_SECRET` меняет и эти
  хеши: повторное событие install того же устройства после ротации секрета
  запишется как новое.

## Границы защиты (читать перед доверием)

Механизмы выше — про **стоимость абьюза и защиту кошелька**, а не про
невзламываемость. Известные границы модели доверия:

- **Идентичность клиентогенерируемая.** device id создаётся приложением и
  никак не аттестуется (Play Integrity/App Attest в планах — см. Roadmap).
  Любой, кто разобрался в протоколе, может генерировать новые id; лимиты
  лишь делают это неудобным и небесплатным по времени/IP, но не невозможным.
- **Ротация с разных IP.** Пару `LIMIT_IP_DISTINCT_DEVICES_DAY` +
  `LIMIT_FRESH_DEVICE_DAY` обходит тот, у кого много адресов (ботнет, пул
  прокси): каждый новый id с нового IP получает свежую квоту в 15 запросов.
  Глобальные дневные потолки — единственный жёсткий предел ущерба в этом
  сценарии.
- **Доверие к прокси — конфигурационное.** `TRUST_PROXY=true` без собственного
  реверс-прокси перед бекендом = любой клиент подделывает свой IP одним
  заголовком (см. чеклист в [ops/DEPLOY.md](ops/DEPLOY.md)).
- **Состояние одного инстанса.** Лимиты живут в SQLite на одном сервере;
  вторая реплика за балансировщиком = независимые квоты. Горизонтального
  масштабирования нет (Roadmap: Redis).
- **Рефералы без аккаунтов.** Email не подтверждается: чужой адрес может
  попасть в счётчик, а установки с эмуляторов и переустановок не отличить от
  настоящих без аттестации устройства — поэтому награду выдаёт человек по
  таблице `/admin/referrals`, а не автоматика.
- **Промпт и схема команд — публичны by design.** Промпт приезжает в каждом
  запросе и живёт в приложении открытым текстом; «пин» гарантирует только,
  что через этот бекенд нельзя прогнать произвольный чужой промпт.

## Быстрый старт

```bash
bun install
cp .env.example .env        # для разработки подойдёт как есть
bun run dev                 # сервер на :8080 (нужен стаб DeepSeek — см. ниже)
bun test                    # юнит- и golden-тесты
bun run smoke               # end-to-end самопроверка реального сервера
```

Для локальной разработки без ключа DeepSeek поднимите стаб (он же участвует
в smoke):

```bash
bun run scripts/stub-deepseek.ts     # :8901, режимы STUB_MODE=valid|garbage|slow
DEEPSEEK_BASE_URL=http://127.0.0.1:8901/v1 bun run dev
```

Генератор нагрузки:

```bash
bun run scripts/load.ts --url http://127.0.0.1:8080 --duration-sec 30 --rps 20
```

## Структура репозитория

| Путь | Что там |
|---|---|
| `src/` | Код: `api/` роутер, рефералы и админка, `referral/` данные/ретеншн, `contract/` гард команд, `identity/` HMAC, `limiter/` ярусы, `llm/` пайплайн и DeepSeek, `server.ts`, `main.ts` |
| `contract/` | HTTP-контракт (`api.md`), схема команд v4, golden-фикстуры парсера |
| `scripts/` | `stub-deepseek.ts` (стаб upstream), `smoke.ts` (e2e), `load.ts` (нагрузка) |
| `ops/` | Dockerfile, docker-compose, Caddyfile, systemd-юнит, [DEPLOY.md](ops/DEPLOY.md) |

Контракт зеркалит приложение: `contract/schema-v4.md` ↔
`lib/magic_input/task_command.dart` + `magic_response_parser.dart`, промпт
`src/llm/prompt.ts` ↔ `lib/magic_input/magic_prompt.dart`. Менять — синхронно
в обоих репозиториях.

## Contributing

PR принимаются: тесты (`bun test`), typecheck (`bun x tsc --noEmit`) и
e2e-смоук (`bun run smoke`) обязаны быть зелёными — их же гоняет CI.
Инварианты репозитория (ноль runtime-зависимостей, HMAC-only хранение,
зеркало контракта с приложением) — в [AGENTS.md](AGENTS.md); изменения
схемы команд и пин промпта синхронны с приватным репозиторием приложения,
такие PR без синхронной пары не смёржатся. Коммиты — атомарные, один
логический смысл на коммит.
