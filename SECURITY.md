# Security Policy

## Supported versions

Поддерживается только последняя версия ветки `main`.

## Как репортить уязвимость

**Не открывайте публичный issue** для security-проблем, включая DoS-сценарии
против лимитера, обход идентификации и инъекции в пайплайн.

Два приватных канала:

- **GitHub**: вкладка Security → «Report a vulnerability» (private vulnerability
  reporting) — предпочтительно.
- **Email**: sarfex@gmail.com (тот же контакт, что в метаданных коммитов).

Пожалуйста, включите в репорт: описание, шаги воспроизведения, влияние и
(если есть) патч. Ответа ждать до 7 дней; публичное раскрытие — после фикса
и релиза, если вы не настаиваете на более раннем скоординированном сроке.

## Данные и админка

Бекенд хранит email (реферальные коды) и IP клиента
при событии установки (срок — `IP_RETENTION_DAYS`). Эти данные доступны только
через `/admin/*`, закрытые токеном `ADMIN_TOKEN` (без токена админка отключена).
Утечку токена, обход авторизации админки, SQL-инъекции в этих путях и чтение
чужих данных репортьте приватно, как описано выше.

## Что НЕ считается уязвимостью

Границы модели доверия задокументированы в README («Границы защиты») и
считаются известными ограничениями дизайна, а не багами:

- генерация новых device id клиентом (идентичность клиентогенерируемая,
  аттестации нет);
- ротация идентификаторов с большого числа разных IP;
- чтение системного промпта и схемы команд (публичны by design, ездят
  в каждом запросе приложения);
- неподтверждённый email в реферальном коде (владение адресом не проверяется
  сознательно, награду выдаёт человек вручную);
- накрутка реферальных установок с эмуляторов/переустановок (решается ручной
  проверкой таблицы, аттестации устройства нет);
- исчерпание лимитов добросовестными запросами (на то они и лимиты).
